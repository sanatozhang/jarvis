# Apollo 平台化升级方案

**汇报人：** sanato
**日期：** 2026-08-25
**数据周期：** 2026-07-13 ~ 2026-08-23（近 6 完整周）
**面向读者：** 各级管理者

> Apollo 是 Plaud 内部的客诉工单智能分析平台。用户在 Zendesk 报修后，客服把工单交给 Apollo，Apollo 自动下载设备日志、定位问题原因、给出可以直接发给用户的回复话术。
>
> 本文汇报三件事：**现在做到了什么、这半年建成了什么、下一步要做什么。**

---

## 0. 一页摘要

**现状**：Apollo 每周处理 56 个客诉工单，其中约 88% 客服看完 AI 的分析就能自己回复用户，不需要找工程师。单个工单从提交到出结论平均 **4 分 45 秒**，而这件事过去要排队等工程师有空，常常跨天。平台运行成本约 **$420/月**。

**进展**：完整的自动化链路已经跑通并稳定运行 5 个月——工单自动接入、日志自动解密处理、AI 定位根因、需要工程师时自动建群转交。工程师的排查经验已经沉淀成 10 类可维护的经验手册。更进一步，**Apollo 积累的工单数据现在已经能反过来告诉工程该往哪投入**——哪类客诉最集中、涨跌趋势怎么样，投入聚焦到哪、客诉量就真的会降下来，这是它从"客服工具"升级为"决策输入"的标志。

**下一步三件事**：

| 方向 | 目标 |
|---|---|
| **1. 全平台接入** | 从只服务手机 App，扩展到 Web、Desktop、后端服务。这是优先级最高的一块——目前占比最大的一类客诉（会员支付相关）恰恰需要后端数据才能查清 |
| **2. 源码安全审计** | Apollo 目前能直接读写公司几乎全部客户端源码。现在靠内网隔离保护，上云前必须先把这条访问路径收紧 |
| **3. 内部上云** | 摆脱两台内网机器手工维护的现状，改为云端托管、公司账号登录、不再需要连 VPN |

## 1. 项目现状

### 1.1 规模与效果

| 指标 | 当前值 |
|---|---|
| 每周进入 Apollo 的工单 | **56 单** |
| 客服拿到分析结果后自己处理掉 | **每周约 49.5 单（88%）** |
| 需要转给工程师的 | **每周 6.5 单（12%）** |
| 单个工单分析耗时 | **平均 4 分 45 秒** |
| 平台运行成本 | **约 $420/月**（年化约 $5,000） |

**响应速度**

过去客服遇到需要看日志才能判断的问题，只能把工单转给工程师，然后等——等工程师手上的活告一段落、等他下载日志、等他排查完再回话。这个过程常常跨天，用户在等待期间的体验是最差的。

现在客服提交工单后 **4 分 45 秒**就能拿到问题原因和一份可以直接发送的回复话术，用户在同一次对话里就得到了答复。

**节省工程师时间**

每周 49.5 个工单不再需要工程师参与。这些工单过去即使最后判断"不用我处理"，工程师也得先花时间看一遍才能下这个结论。按每单约 20 分钟估算，Apollo 每年为工程师团队省下约 **860 个工时**（估算值）。

对比 $5,000/年 的运行成本，这笔投入的回报关系是清楚的。

### 1.2 当前支持范围

| 端 | 状态 |
|---|---|
| 手机 App（iOS / Android） | 生产主力，占工单量约 99% |
| MCP（开发者接口对接问题） | 已接入运行，量小但在增长（近 3 周 6 单，此前 3 周 1 单） |
| Web / Desktop / 后端服务 | **尚未接入** |

工单的平台分布上，**iOS 与 Android 大约是 3.2 : 1**（近 6 周 176 单 vs 55 单）。

## 2. 项目进展

### 2.1 已建成的能力

这半年建成的是一条完整的自动化链路，不是零散的功能点：

```
        工单进来                    Apollo 自动处理                     结果出去
   ┌──────────────┐      ┌──────────────────────────────┐      ┌──────────────┐
   │  飞书工单表   │      │  1. 下载日志                  │      │  问题分类     │
   │  客服表单     │─────▶│  2. 解密（私有加密格式）       │─────▶│  根本原因     │
   │  Linear      │      │  3. 截取问题发生时段           │      │  关键日志证据 │
   └──────────────┘      │  4. 压缩重复噪音              │      │  客服回复话术 │
                         │  5. 翻经验手册找相似案例       │      └──────┬───────┘
                         │  6. AI 结合日志+源码分析       │             │
                         └──────────────────────────────┘             │
                                                                       │
                                    ┌──────────────────────────────────┴──┐
                                    │                                     │
                              客服自己回复用户                    需要工程师
                              （每周约 49.5 单）                （每周 6.5 单）
                                                                          │
                                                                          ▼
                                                            自动建飞书群 + 拉值班人
                                                                + 推送完整背景
```

平均耗时 **4 分 45 秒**。

| 能力 | 说明 |
|---|---|
| **工单自动接入** | 飞书工单表、客服提交表单、Linear 三个入口的工单自动进入分析队列，无需人工搬运 |
| **日志自动处理** | 设备日志自动下载、解密（Plaud 设备日志是加密的私有格式，人工无法直接阅读）、按问题发生时间截取相关时段、压缩掉重复噪音后交给 AI |
| **AI 根因分析** | 输出问题分类、根本原因、关键日志证据、给客服的回复话术、以及是否需要工程师介入的判断 |
| **经验手册** | 工程师的排查经验已沉淀为 10 类可持续维护的规则，覆盖蓝牙连接、会员支付、硬件固件、云同步、录音丢失、声纹上云、文件传输、时间戳、App 崩溃、开发者接口对接。更新手册不需要发版 |
| **工程师转交闭环** | 判断需要工程师时，自动创建飞书群、拉入当周值班人、推送带完整背景的通知 |
| **值班管理与看板** | 值班排期、工单分布统计、准确率看板 |

### 2.2 分析质量现状

如实呈现，不修饰：

- 已闭环的转交工单，**平均 6.8 天**解决，最快当天完成
- 问题类型识别覆盖 10 类；近 6 周 AI 给出"有把握"结论的比例为 **22%**
- 6 月底底层 AI 模型换代后，把握度出现了波动。原因已经定位清楚（换代后的适配调整尚未补齐，以及疑难工单需要的深度核对工具需要扩充），修复方向明确，会单独推进

### 2.3 能力延伸：Apollo 自己就能看出客诉集中在哪、趋势怎么走

这是本次汇报里最值得单独说的一节。

Apollo 现在不只是"一单一单地分析"，处理每张工单时会顺手把问题归到一套标准分类体系里。攒够工单量之后，就能自动看出：**最近的客诉集中在哪几类、涨跌趋势怎么样、该往哪个方向投入**。这是 Apollo 自己生产数据里已经跑出来的结果，不依赖任何外部数据源。

#### A. 近 6 周，Apollo 处理的工单里，这几类最集中

| 问题类别 | 近 6 周单量 | 环比（近 3 周 vs 前 3 周） |
|---|---|---|
| 云同步与录音存取 | 87 | 42 → 45，-6.7% |
| 蓝牙 / 设备连接 | 59 | 26 → 33，-21.2% |
| 查找设备 | 31 | 8 → 23，**-65.2%** |
| 账号与登录 | 30 | 12 → 18，-33.3% |
| 设备管理 | 28 | 11 → 17，-35.3% |
| 转写效果 | 24 | 9 → 15，-40.0% |
| 开发者接口对接 | 24 | 8 → 16，-50.0% |
| 固件 | 23 | 5 → 18，**-72.2%** |

**这张表要看两件事**：一是总量——"云同步与录音存取"单量最大，是当前投入优化优先级最高的一类；二是降幅——"查找设备""固件"这两类降幅最猛，正好是近期有专项修复投入的方向，**说明工程投入聚焦到哪，客诉量就真的会降下来**，Apollo 的分类统计能直接验证这件事，也能用来判断下一步该把资源往哪调。

**值得单独说明的一点**：会员 / 订阅相关的问题，在 Apollo 自己近 6 周处理的工单里只有个位数——不是这类问题真的少，而是它们大多要查后端的订单和支付记录，App 日志查不出答案，今天基本进不到 Apollo 的分析范围，客服只能手动处理或者搁置。这正是下面 §3.1 里要优先接入后端服务的原因。

## 3. 下一步规划（一）：全平台接入

**这是优先级最高的一块。**

目标：Apollo 从"只服务手机 App"变成"服务全部端"。

### 3.1 接入的核心难点：每个端手里的"证据"不一样

Apollo 判断一个问题的根因，靠的是三样东西凑在一起看：**用户怎么描述问题、设备当时的运行日志、对应的代码**。App 三样都齐全，这也是它今天效果好的基础。但换一个端，证据就不齐了，分析方式也要跟着变：

| 端 | 用户描述 | 运行日志 | 代码 | 分析方式要怎么变 |
|---|---|---|---|---|
| App（现状基准） | 有 | 有 | 有 | 三样齐全，是今天默认的分析方式 |
| MCP（开发者接口对接） | 有 | 通常没有 | 有 | 已经在用"没有日志就不硬猜"的分析方式，效果可用 |
| Desktop（桌面客户端） | 有 | 有，但格式跟 App 不一样 | 有 | 复用度最高，把日志格式适配好，就能直接跑通默认分析方式 |
| Web（网页版） | 有 | **没有**——浏览器本身不产生这种本地日志文件 | 有 | 必须换一条路走：不读日志文件，改成直接查后台服务当时记录了什么。这是分析方式本身的改变，不是"多适配一种日志格式"就能解决的 |
| 后端服务 | 有（用户侧的描述） | 有服务端记录，但**目前跟 App 侧的日志对不上号**——两边没有统一的关联线索，没法确认是不是同一次操作 | 有 | 要先建立"App 侧和后端侧记录的是同一件事"这层对应关系，才能把两边证据拼成一条完整链路 |

**这就是为什么"支持 Web / Desktop / 后端"不是简单的开关问题**：Desktop 改动最小，换一下日志格式就行；Web 要新建一条完全不同的取证路径；后端不仅要新建路径，还要先解决"两边记录怎么对应上"，才能真正发挥价值——也就是下面 §3.2 里那 8,992 单客诉对应的部分。

好消息是：现有链路里的大部分环节（日志时段截取、噪音压缩、AI 分析编排、经验手册匹配、结果解析、转交流程）都与具体是哪个端无关，可以直接复用，不用重新造。

### 3.2 接入计划

| 接入对象 | 要做的事 | 前置依赖 |
|---|---|---|
| **多端基础设施** | 让"哪个端"这个信息真正参与问题识别；新端工单的独立存储接线；表单采集各端专属信息；统计报表增加端的维度 | 无 |
| **Desktop（桌面客户端）** | 补齐桌面端日志的解析处理；把日志时间格式做成可扩展的；编写桌面端经验手册 | 需 Desktop 团队提供日志样本 |
| **Web（网页版）** | 打通"直接查询后台运行数据"的通道——这条路在崩溃监控模块里已经有可复用的成熟做法，不用从零发明；同时表单要采集出问题的页面地址、浏览器、会话标识；编写 Web 经验手册 | 依赖上述查询通道 |
| **后端服务** | 端的注册与代码仓路由；确认后端日志形态；打通 App 侧与后端侧的关联线索；编写后端经验手册 | **需 BE 团队先确认日志形态（当前阻塞项）** |

**价值锚点**：从 Zendesk 全量客诉看，"设备 / 会员绑到了错误的账号""付了钱但会员权益没生效""购买后权益或确认邮件没收到"这三类问题近 6 周合计 **8,992 单**，全部是"钱和权益的真相在服务器上"的问题——App 日志最多只能看到"用户点了购买按钮"，之后订单状态、支付回调、权益发放，App 完全不知道。这类客诉目前也基本进不到 Apollo 的工单里（前面 §2.3 提到过，Apollo 自己近 6 周处理的会员 / 订阅类工单只有个位数），只有接入后端服务、并且打通两侧关联线索之后，才具备被自动分析的可能。这是全平台接入里回报最直接的一块。

## 4. 下一步规划（二）：源码安全审计

**这部分已经启动**：代码安全评估申请已提交，安全团队正在评估中。下面是我们自己梳理出的风险点，作为评估的参考输入，也是后续的整改方向。

### 4.1 核心风险

Apollo 要判断一个 bug 的根因，往往需要对照源码来看。为此，**Apollo 目前可以直接访问公司几乎全部客户端源码仓库**：

- App 主仓（Flutter）
- Native 新架构仓（Android / iOS）
- Web 仓
- Desktop 仓
- 开发者工具仓

而且是**可读可写**。同时，运行 Apollo 的机器上还存放着用于向仓库提交代码的账号凭证。

> **一旦 Apollo 所在的机器被入侵，等于公司客户端源码全部泄漏，并且攻击者能用我们自己的开发者身份往代码仓库里推送代码。**

目前挡在前面的唯一一层保护是"部署在内网、访问需要连 VPN"。**上云之后这层保护就没有了**，所以源码访问这条路必须在上云之前收紧。这是整个上云计划的前置条件，不是可选项。

### 4.2 其他已识别的风险点

除了源码泄漏这个最大的风险，排查过程中还发现几个需要一起处理的问题：

| 风险点 | 说明 |
|---|---|
| **部分管理功能没有身份校验** | 修改分析规则、修改系统设置等操作，目前任何能连上内网的人都能做，不需要登录验证。最坏情况下，这个口子理论上能被用来在服务器上执行任意指令 |
| **用户日志的加密强度不够** | 设备日志解密用的密钥写死在代码里，所有用户共用同一把，且从未更换过。一旦代码泄露，历史上所有用户的日志都有被解密的风险 |
| **一份包含全部凭证的备份文件曝露在外** | 机器上有一份数据库、各类密钥的完整备份文件，没有被正确排除在代码版本管理之外。一旦代码仓库的访问权限扩大，这份文件会跟着一起泄露（已发现，需要尽快清理） |
| **用户日志没有保留期限** | 分析过程中下载、解密出来的用户日志，目前没有自动过期清理机制，会无限期堆在服务器上 |
| **关键操作留痕不完整** | 谁下载过用户日志、谁修改过分析规则，目前部分场景没有记录到具体是谁操作的，出问题难以追溯 |

### 4.3 整改方向

| 方向 | 内容 |
|---|---|
| **源码访问收口**（最高优先） | 源码从"常驻、可写"改为"按需获取、只读、用完即清"；提交代码改用权限受限的应用身份（只授予必要仓库的必要权限），不再使用个人开发者凭证；去掉机器上常驻的密钥 |
| **分析进程隔离** | AI 分析进程降权、沙箱化，不再与主服务共享同一套权限 |
| **身份与权限** | 启用公司账号统一登录、全部接口强制身份校验、按角色分配可见范围、启用加密传输 |
| **数据与隐私** | 用户日志设定保留期并自动清理；敏感信息在进入分析前脱敏；日志加密密钥轮换（需客户端配合，作为长周期项立项） |
| **审计留痕** | 关键操作留下可追溯记录：谁触发了分析、谁修改了经验手册、谁下载了用户日志 |
| **工程流程** | 建立持续集成检查、凭证泄漏扫描、依赖版本锁定 |

## 5. 下一步规划（三）：内部上云

目标：摆脱"两台内网机器手工维护"的现状，不再需要连 VPN。

| 方向 | 内容 |
|---|---|
| **存储与数据库** | 单机数据库改为云托管数据库；本地工作目录改为云对象存储（顺带解决用户日志保留期的问题） |
| **运行时** | AI 服务的访问凭证从"人工登录维护"改为托管密钥自动管理，不再需要人工定期上机器重新登录 |
| **访问方式** | 公司账号一键登录，不用连 VPN、不用手填用户名；按角色控制可见范围，操作可追溯到具体的人 |
| **上线配套** | 域名、证书、监控告警、容器编排 |

## 6. 终局链路

### 6.1 设计理念：Linear 工单是唯一的核心载体

终局链路的关键不是"把几个系统连起来"，而是**让 Linear 工单成为一个客诉从进来到解决的唯一主线**。

用户的问题从 Zendesk 进来，最终变成一张 Linear 工单。之后无论是 Apollo 分析、值班同学跟进、跨团队交接、还是最终结论沉淀，**全部挂在这一张工单上**。这样做的价值：

- **责任永远清晰**：工单当前在谁手上、处于什么阶段，看状态就知道，不需要在群里问"这个谁在跟"
- **交接不丢上下文**：App 值班同学分析后发现是后端的问题，直接把工单流转给后端值班，Apollo 的分析结论、日志证据、用户原始描述都在工单里，接手的人不用重新问一遍
- **数据可沉淀可分析**：每张工单都留下了"什么问题、谁处理、流转过几手、多久解决、根因是什么"的完整记录，这些数据才是后续做趋势分析、产品建议（§2.3）的原料

### 6.2 完整链路与状态流转

```
┌──────────────┐
│   Zendesk    │  用户报修，客服判断需要技术排查
└──────┬───────┘
       │  ① 自动创建
       ▼
┌─────────────────────────────────────────────────────────────┐
│                    Linear 工单（核心载体）                     │
│                                                              │
│   状态：Todo ──▶ AI 分析中 ──▶ 待跟进 ──▶ 处理中 ──▶ Done    │
│                     │            │          │                │
│         ┌───────────┘            │          └──────┐         │
│         │                        │                 │         │
│   ② Apollo 自动分析        ③ 指派值班同学     ④ 跨端流转      │
│      写入根因/证据/          App oncall        App → BE       │
│      建议话术                                   oncall        │
│                                                              │
│   ⑤ 解决后写入结论：根因分类 / 修复版本 / 处理耗时             │
└──────┬───────────────────────────────────────────────────────┘
       │  每次状态变化都通知
       ▼
┌──────────────┐
│    Slack     │  分析完成、需要接手、已解决 → 对应频道/个人
└──────────────┘
```

**一个典型的跨端流转例子**（正是最需要多端接入的场景）：

1. 用户报"付了钱但会员没生效" → Zendesk → 自动建 Linear 工单，状态 `Todo`
2. Apollo 自动分析 → 状态自动变 `AI 分析中` → 分析完写入结论：App 侧日志只到"发起购买"，之后无记录 → 状态变 `待跟进`，Slack 通知 App 值班
3. App 值班同学看了结论，确认 App 侧没问题 → **把工单流转给后端值班** → 状态 `处理中`，负责人变更，Slack 通知后端值班
4. 后端值班查到支付回调失败的原因，修复后在工单里写结论、标记修复版本 → 状态 `Done`，Slack 通知客服可以回复用户
5. 这张工单的全过程（问题类型、流转路径、耗时、根因、修复版本）进入数据池，供趋势分析使用

### 6.3 当前各环节状态

| 环节 | 状态 | 说明 |
|---|---|---|
| Zendesk → 自动创建 Linear 工单 | ❌ 未打通 | 目前只能读取 Zendesk，不能写入 |
| Linear → Apollo 分析 | ✅ 已打通 | 在工单里触发即可自动分析 |
| Apollo 分析结论写回 Linear | ⚠️ 部分 | 能添加评论和标签，**但改不了工单状态** |
| Linear 状态自动流转 | ❌ 未打通 | 需要新增改状态的能力 |
| 跨端 oncall 交接 | ⚠️ 部分 | 目前转交靠自动建飞书群，与 Linear 工单状态没有联动 |
| 完成后通知 Slack | ❌ 未打通 | 目前通知走飞书，Slack 尚未集成 |
| 结论结构化沉淀 | ⚠️ 部分 | Apollo 内部有记录，但没有和 Linear 工单打通形成统一数据源 |

→ **要打通的核心是"改状态"和"Slack 通知"这两块能力**，其余环节已有基础。
